DEV BRIEF

Magento 1 → BigQuery sales mirror.

Goal

Mirror sales-relevant tables from our Magento 1 + BoostmyShop store into BigQuery so the data is queryable alongside our other analytics, ready for dashboards and automated reporting. Nightly sync, no real-time required.

Internal · share with developers only

The steps below are everything the dev needs to scope and execute. Anything marked TBD comes back from you.

STEP 01 — ACCESS

Access we need from you

  • A read-only MySQL user scoped to the tables in the next section.
  • Strongly preferred: a read replica, not prod. Magento 1 prod DBs do not tolerate analytical queries well.
  • Connection details: host, port, database name, credentials.
  • VPN / IP allowlist instructions for whichever runtime executes the extractor.
STEP 02 — TABLES IN SCOPE

What to mirror

PurposeTables
Orders sales_flat_order, sales_flat_order_item, sales_flat_order_address
Finance sales_flat_invoice, sales_flat_creditmemo, sales_flat_creditmemo_item
Products catalog_product_entity + catalog_product_entity_varchar/int/decimal/text (or catalog_product_flat_<storeId> if enabled)
Categories catalog_category_entity, catalog_category_product
Customers customer_entity, customer_address_entity
BoostmyShop erp_purchase_order, erp_purchase_order_item, erp_supplier, bms_stock, bms_inventory — exact names vary by BMS version, run SHOW TABLES LIKE 'erp_%' and 'bms_%' to confirm.
STEP 03 — DESTINATION

Where it lands

  • GCP project: welzyn
  • New dataset: welzyn.Magento_<storeslug> in the same region as our existing reporting datasets (required for cross-dataset joins).
  • One BigQuery table per source table.
  • Partition order tables by DATE(created_at); cluster by store_id where applicable.
  • Service account scoped with roles/bigquery.dataEditor on the new dataset only.
STEP 04 — DELIVERABLES

What to build

Backfill

One-shot historical load from store inception (or an agreed cutoff date) into the BigQuery dataset.

Nightly incremental

Scheduled run at 03:00 Europe/Madrid (must complete before reporting jobs at ~07:00):

  • Filter each table by updated_at > <last watermark>; fall back to created_at where updated_at is absent.
  • MERGE into BigQuery on the table's primary key (entity_id for sales/catalog tables).
  • Persist watermark per table (Cloud Storage object or a small _sync_state table in BigQuery — your call).

Schema tolerance

Handle new source columns without breaking. Fail loudly on type changes — those need our review.

Reconciliation

Automated check at the end of each run: yesterday's completed-order count and SUM(base_grand_total) in BigQuery should match Magento admin → Sales → Orders within rounding. Alert on mismatch.

STEP 05 — GOTCHAS

Magento 1 quirks to handle

  • Currency. Use the base_* money columns (base_grand_total, base_subtotal, base_tax_amount, base_shipping_amount). Never the non-base_ versions — those are in each order's display currency. Our reporting standard is EUR throughout.
  • Order state filter. "Real" revenue is state IN ('complete','closed','processing'). Load canceled and holded too, but tag them. Don't drop at extract time — let analytics decide.
  • Refunds live in sales_flat_creditmemo*, not as negative orders.
  • Time zone. Magento 1 default for created_at is UTC, but confirm via core_config_data (general/locale/timezone). Store the UTC value in BigQuery; convert at query time.
  • Configurable products. sales_flat_order_item carries one row for the configurable parent and one for the simple child. Keep both rows; expose parent_item_id so analyses can pick the right one.
  • EAV joins. Product attributes (name, SKU, price) require joins through the catalog_product_entity_* tables unless flat catalog is enabled. If flat is on, prefer it.
  • Soft deletes. Magento 1 doesn't really soft-delete — cancelled and holded orders persist with state changes. Do not filter them at extract time.
STEP 06 — STACK

Suggested stack (pick anything equivalent)

  • Python with PyMySQL + google-cloud-bigquery.
  • Cloud Run Job + Cloud Scheduler, or cron on an existing host — whichever is simpler for you.
  • MySQL credentials in Secret Manager.
  • Avoid Airbyte / Fivetran — overkill for this scope and adds a managed-service line item.
STEP 07 — OUT OF SCOPE

Explicitly not in v1

  • Real-time / streaming sync. Daily is enough.
  • Writing back to Magento.
  • Any frontend dashboard. Data is consumed downstream from BigQuery.
STEP 08 — ACCEPTANCE

Acceptance criteria

  • All listed tables present in welzyn.Magento_<storeslug>; row counts within 0.1% of source after backfill.
  • Nightly job runs green for 7 consecutive days.
  • Reconciliation check on yesterday's revenue passes within rounding.
  • Short runbook in the repo: how to re-run a failed sync, how to backfill a single table, how to add a new table.
STEP 09 — CONFIRM BACK

Please reply with

  1. Read replica or prod?
  2. Approximate row count of sales_flat_order.
  3. Preferred runtime — Cloud Run Job, GKE cron, or an existing host.
  4. Any existing service-account / project conventions we should reuse.
